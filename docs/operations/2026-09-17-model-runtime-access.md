# 模型接入自动同步调用授权

已更新到现有公网 8060 平台，当前运维入口为 `data/agent-releases/20260917-model-runtime-access/manage.sh`，后端镜像为 `ruoyi-backend-pg:model-runtime-access-20260917`。前端继续使用知识图谱版本。

## 原因与行为

接入向导会自动生成部署别名并保存绑定，但原发布流程只查询内部 Runtime Key 的可见模型，不同步该 Key 的 models 白名单。线上 GLM 5.3 部署已存在，其自动别名未在仅包含 DeepSeek 和 Embedding 的白名单中，发布因此停留在草稿。

- 发布时先查 Runtime Key 的可见模型；缺失则按精确别名查询真实部署，只追加当前别名到该 Key 的模型列表，再验证运行时可见性并发布。
- 不要求用户填写别名，不增加前端字段。已有可见模型发布无需调用管理接口；失败保留配置和草稿，提示重试或检查后台权限。
- 只更新固定后台 Runtime Key 的 models；用 SHA-256 摘要和 POST 正文定位密钥，不把明文密钥放入 URL。已有模型、预算、角色及其他配置保留，拒绝把通配别名作为新增授权。
- 使用 PostgreSQL 事务级咨询锁串行化各进程的读改写。总同步预算 20 秒；已发出的更新在取消或超时后继续持锁等待 HTTP 操作结束，再释放锁，避免晚到写入覆盖后续授权。
- 按 `model=alias` 查询部署并复核返回别名，避免 LiteLLM 默认只返回前 50 项导致误判。

实际模型调用还发现目录创建时将共用默认参数 VO 的所有空字段写入数据库，导致 Chat 模型被 `dimensions: null` 等字段拒绝。创建和更新现只保存非空默认参数；读取旧目录时兼容已知默认字段的 null，未知字段和非空跨类型参数仍被拒绝，不需修改已有用户数据。

## 验证与线上结果

- 修复前复现新模型缺少 Runtime 授权，以及 Chat、Embedding、Rerank 共 6 个默认参数回归失败；修复后相关后端测试 **246 passed**。有一条既有 async-lru 测试事件循环切换警告。
- 自动别名前端契约、模型转换测试、Ruff、diff 检查及镜像 `pip check` 通过。独立审查发现的写入取消竞态和部署分页问题均修复并复审通过。
- 使用真实 PostgreSQL 两个独立会话确认咨询锁串行、释放后可再次获取；实际 LiteLLM 摘要查询、精确存在/不存在部署查询通过。
- 在生产镜像 Python 3.10.17 验证写入期间重复取消和超时，锁保持到写入完成，后续发布保留两个新增模型。
- 通过正常 ModelCatalogService 对现有 `zai-org-glm-5.3` 草稿重试发布，状态从 draft 变为 active，运行时从不可见变为可见。运维操作署名 `codex-ops`。
- Runtime Key 白名单仅从 `deepseek-v4-flash-chat`、`qwen3-vl-embedding` 增加 `quick-zai-org-glm-5.3-bbc0dc7a`，未授权另一条未使用的 Quick DeepSeek 部署。
- 使用最终镜像的正常 ModelService 对真实 GLM 发起短请求，返回 HTTP 200、2 个回复字符、38 个输出 token，约 1.42 秒；测试没有创建聊天历史。
- 仅重建后端容器，保留原知识图谱、文件、知识库持久化挂载和所有基础服务。前端首页哈希保持 `9f4692c6f991e924ee134dc17711b82f08addb147813ed4bb60a0bf26d05d85f`，公网验证码入口正常。

## 运行边界与回退

自动授权锁依赖当前 PostgreSQL 部署。本次未提供 MySQL 锁兼容，符合当前平台仅使用 PostgreSQL 的约定。

LiteLLM 的更新接口不是跨服务事务：网络自身超时或断连可能使写入结果暂时不确定，应重试发布并重新确认可见模型。应用取消不会提前释放正在执行更新的锁。一个非阻塞边界是：整体超时后进入清理阶段，再收到外部取消时最终可能报告同步失败；不影响持锁和授权一致性。

回退可使用前一知识图谱发布入口重建后端，但会重新暴露新增模型授权缺失和默认参数 null 的问题。已经追加的具体模型授权无需撤销，切勿清空 models 或替换密钥。此前知识图谱版本的数据保留与回退要求继续有效。
