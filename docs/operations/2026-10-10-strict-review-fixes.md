## 资源归属与旧库升级

新增表为 `sys_plugin_resource_ownership`，没有指向 `sys_plugin` 的外键，因而不随平台元数据清理而级联删除。它保存资源类型、历史回调及以下状态：

| 状态 | 含义与处理 |
| --- | --- |
| `none` | 确认从未安装且无历史责任，跳过业务表查询；新的迁移/安装证据不能被这个旧标记覆盖 |
| `retained` | 已完整安装并保留资源检查责任；安全卸载与元数据 purge 都保留该记录 |
| `unknown` | 旧历史或部分安装无法可靠判断，拒绝不完整检查；完整重装可以恢复可信状态 |

已有 `none` 与实际安装记录矛盾时，清理前会保留安装证据：能取得源码则捕获回调并转为 `retained`，否则转为 `unknown`。已有 unknown 不会因一次普通清理被判定成无责任。

引用端口在调用方会话中执行单条证据查询，不提交、不回滚、不显式开启事务，也不刷新调用方待提交对象。查询结果使用标量快照，避免同一会话中已加载的 ORM 旧状态遮蔽数据库里的新责任。普通 SELECT 仍遵循数据库隔离级别及 SQLAlchemy 的隐式事务规则。

旧数据库升级步骤：

1. 先备份平台业务库和实例配置，并核对当前部署版本；本轮没有替运行实例执行备份或迁移。
2. 对**平台业务库**执行对应的幂等增量建表 SQL：[PostgreSQL](../../zhiheng-fastapi-backend/sql/upgrades/postgresql/20261010_plugin_resource_ownership.sql)、[MySQL](../../zhiheng-fastapi-backend/sql/upgrades/mysql/20261010_plugin_resource_ownership.sql)。它们只新增归属表，不清空旧表；不要对已有库执行含 DROP 的完整初始化 SQL。
3. 新版 Web 服务正常启动时已有 `create_all` 流程也会创建该表。独立 CLI 不经过这段启动流程，应先执行增量 SQL，或先完成新版服务建表。
4. 核对插件状态及引用检查。旧版已卸载记录与从未安装记录可能完全相同，不能凭迁移成功或可清理的审计日志猜测；unknown 导致删除被拒绝时，应恢复完整源码并通过完整重装等受控流程恢复可信状态。

回调重命名需保留历史兼容入口。当前 purge 保守保留检查责任，没有新增“业务已清空”的自动解除契约；如果 purge 删除了业务表、源码或回调，需要恢复有效检查能力。不要通过直接把归属设成 none 来绕过保护。升级前已经删除全部平台状态和历史证据的遗留数据，无法由新表自动识别。

**新表改变了发布包的数据契约。** 旧包与包含新表的版本不能直接执行快捷跨契约更新/回滚，也不能篡改 `release.json` 绕过检查。应先制定并验收专项迁移方案；本次修复没有提供自动跨契约迁移或数据库降级。
