# 知识图谱构建失败修复

本版修复实体抽取超时及图谱批量向量生成失败。后端镜像为 `ruoyi-backend-pg:graph-build-reliability-20260918`，运维入口为 `data/agent-releases/20260918-graph-build-reliability/manage.sh`，前端沿用历史列表统一版本。

## 根因

2026-09-18 09:05 至 09:09 的任务共 3 个文档，全部图谱失败，原有向量索引状态为 done。

- 两个文档在 DeepSeek 实体抽取阶段触发 90 秒超时。同一 hosts 内容和提示词延长至 240 秒仍超时，只限制输出4096也未解决；通过同一模型发送固定 `extra_body.thinking.type=disabled`，4.16 秒返回完整结果。因此使用显式模型名单仅对图谱调用关闭思考。
- 另一文档已经得到 14 个实体、13 条关系，但向量模型在超过8条输入时返回重复编号。9条返回 `[0,1,2,3,4,5,6,7,0]`；14/16条同样重置编号。HTTP仍为200，向量数量与4096维度都正确。按8条拆批后成功。已证实的是当前模型链路响应问题，不据此断言具体由代理还是上游造成。

## 修复

- 主知识库索引和图谱向量调用统一每批最多8条，每批保持索引、维度和模型绑定检查，不猜测不合法向量与文本的对应关系。
- 图谱 LLM 单次输出上限16384，调用超时240秒。保留受控 `finish_reason` 并拒绝 length 截断响应，避免不完整结果被标成构建成功。
- 后端设置 `KNOWLEDGE_GRAPH_DISABLE_THINKING_MODEL_IDS=mdl_3cd85df9eb4b4977a26099601ebdf588`。仅该已验证 DeepSeek 模型的图谱调用携带受限 `thinking_mode=disabled`，adapter映射为固定provider扩展。普通聊天没有此参数，未配置的模型也不会收到扩展。新增模型需要运维确认兼容后加入名单。
- 图谱错误以固定类别保留到文档和任务，区分抽取超时、向量错误、认证、限流、空输出及截断。使用每次插入独立的 ContextVar，防止 SDK 迟到回调把前一文档错误写到后一文档。
- 回调保留局部异步包装函数，避免 LightRAG 深拷贝配置时递归复制绑定方法、图谱实例和存储连接。
