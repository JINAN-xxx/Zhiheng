# 智衡版本化发布与应用回滚

## 目标与范围

用户已授权完善发布与回滚流程。本轮沿用模块化单体，在当前工作区实现可搬运的镜像发布包、独立安装目录、版本校验、健康门禁和应用回滚。保留源码部署入口；不修改运行中的实例，不提交或推送工作区。

可选方案：仅增加镜像标签改动少，但标签会被覆盖且前后端容易错配；依赖镜像仓库适合持续交付，但当前没有指定仓库；因此本轮选择包含镜像归档的离线发布目录，后续可增加仓库分发。发布端需要 Node.js 和 Docker，运行端仅需 Docker、Compose v2 和 Python 3.10+。

## 产物与版本

`./deploy.sh release build --version <版本> --output <目录>` 在临时目录构建当前前端与后端，不覆盖仓库 `dist`。发布目录包含 `release.json`、`images.tar`、独立的 `compose.release.yaml`、`release.sh`、Python 管理脚本及必要运行配置，不包含宿主 `.env`、运行数据和源码工作树。后端镜像仍包含运行必需的 Python 代码和插件前端资源。

清单格式为 `format: 1`，包含 `version`、`created_at`、`source`（revision、dirty、sha256）、`platform`、`compatibility`（data_sha256、runtime_sha256）、`images`（backend、frontend、postgres、redis、litellm、milvus 各自的 tag 和 id）及 `files`（相对路径到 SHA256）。所有镜像随包导出并在加载后逐一核对 ID，版本不可覆盖。文件校验用于发现损坏或错配，不提供发布者签名认证。

后端构建排除所有 `.env*` 与私钥文件。首次部署生成并持久保存实例自己的传输密钥；升级和回滚均复用实例配置。前端资源由镜像提供，运行端不挂载源码或 `dist`。

## 安装与状态

发布目录内执行 `./release.sh deploy --site /绝对路径/安装目录`。安装目录拥有 `.env`、`data/`、`releases/<version>/`、`state.json` 和部署锁。版本目录保存校验后的包；数据目录和环境文件固定在版本目录之外。容器以安装实例标识关联，首次部署拒绝接管同 Compose 项目的既有容器。

操作顺序：校验包与兼容性 → 暂存版本 → 加载并校验镜像 → 校验 Compose → 启动基础服务 → 写入操作日志 → 停止应用写入 → 初始化/迁移校验 → 启动后端和前端并等待健康 → 核对运行镜像 → 原子更新当前与上一版本。修改操作互斥；进程环境不能覆盖清单镜像或实例配置。敏感配置不进入版本清单或命令行输出。

更新失败且存在兼容的上一版本时自动恢复上一应用；恢复失败保留操作记录并明确报错，不宣称成功。中断后可用 `rollback` 恢复记录的原版本；首次部署失败可重试同一版本。`status` 显示当前、上一版本与未完成操作。

## 回滚边界

`./release.sh rollback --site <安装目录>` 切换到上一个成功版本，不执行旧版初始化，不删除数据卷，不还原数据库或文件。回滚后当前与上一版本交换。数据库契约包含完整 SQL、迁移与种子、插件清单、初始化脚本，以及显式的持久数据版本文件；持久 JSON 等格式变化必须提升该文件版本。基础组件镜像与运行编排也纳入兼容性指纹。

快捷升级和回滚要求数据及基础运行契约相同。契约不同在停服务前拒绝，需另行备份和规划数据升级；本轮不提供未经验证的自动数据库降级。保留旧应用产物，不自动清理镜像和历史版本。

## 验证

先写行为测试覆盖版本篡改、镜像错配、路径穿越、私钥排除、实例隔离、持久配置复用、部署锁、失败回退、中断记录、健康门禁和不兼容拒绝。执行现有部署回归与 Ruff；用真实 Docker 构建发布包，在独立项目、端口和数据目录演练首装、升级、回滚及故障恢复，并验证当前运行实例和已有 dist 未变化。记录真实执行与未验证限制。
