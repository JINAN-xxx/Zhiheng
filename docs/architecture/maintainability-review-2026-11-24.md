# DAIP 工程结构与可维护性评审

评审基线为 `feat/workspace-agent`，提交 `44c4ce18`，另含当时工作区尚未提交的助手广场、`0046_assistant_plaza` 迁移和页签体验改动。对象为当前 `backend/src/zhiheng`、`frontend/src`、测试、架构规则和交付配置。目录与依赖做了整体检查，业务链路沿智能助手、知识准备、文件与权限、通用模型执行和工作空间交付重点追踪。未逐行证明全部功能正确，旧工程按约定不纳入评审。

结论：**保留现有模块化单体、Vue 按域分包、API 与 Worker 分进程的结构。** 关键缺口集中在跨层调用、持久状态的版本语义和发布门禁。按目录名称重分包或拆成微服务，无法解决这些问题，还会增加迁移和维护成本。

## P1 · 优先修复

### E01 · 广场迁移降级会丢失会话来源

`0046` 的降级直接移除广场标记和发布配置，保留广场会话与对话。上一版本按会话所有者授权读取，并从当前助手草稿取名称、简介和欢迎语。已有广场会话降级后可能被当成个人会话，读到未上架的展示字段。这个结论来自新旧代码和迁移的静态对照，未对运行库做降级。见 [0046 迁移](../../backend/migrations/versions/0046_assistant_plaza.py#L21) 和旧提交 `44c4ce18` 的 `modules/agents/conversations.py:221,282`。

建议在已有广场记录时显式阻止原地降级，回退时使用升级前备份或向前修复。用隔离库覆盖空记录可降级、有记录拒绝、事务失败不留下半套结构。

### E02 · 未确认提交把正文和附件元数据留在浏览器

助手用 `sessionStorage` 保存整份待确认提交，含消息正文和附件信息。退出或切换账号时会清除组件内存，旧主体的存储项仍留在同一个标签页。按账号区分的键避免正常界面误读，但没有消除共享浏览器上不必要的数据留存。见 [待确认提交](../../frontend/src/modules/agents/composables/useAssistantCommands.ts#L28)、[保存](../../frontend/src/modules/agents/composables/useAssistantCommands.ts#L109)、[重置身份](../../frontend/src/modules/agents/composables/useAssistantCommands.ts#L311)。

建议先在退出和换号时清理旧主体数据，再把恢复链收敛为少量请求标识与按调用者授权的服务端受理查询。验证响应丢失后可以恢复原请求，且不重复发起付费调用。

### E03 · 周期维护与推理消费共用退出和调度路径

Worker 用 `FIRST_COMPLETED` 监听消费、心跳及维护任务。维护循环的普通异常会触发整个进程关闭。恢复过期运行、多个领域的 checkpoint 清理、工作空间恢复在一次维护循环内串行，文件维护还可占用同一循环最多 180 秒。一次非核心清理的慢调用或暂态故障，会拖延租约恢复，或使健康的队列消费者一并重启。见 [Worker 监督](../../backend/src/zhiheng/worker/process.py#L83)、[维护循环](../../backend/src/zhiheng/worker/process.py#L127)、[任务顺序](../../backend/src/zhiheng/worker/maintenance.py#L8)。

建议分开关键运行恢复和清理调度，为各清理职责设置超时、有界重试和可观察状态。保留关键依赖持续失败时退出的行为。验收采用单项清理失败与慢调用注入，验证其他队列继续消费、过期 Run 按期恢复。

### E04 · 源码模式容易把一个工作副本连到另一个实例

`dev.sh` 默认读取现有 API 容器的环境文件，挂载当前 checkout 的源码，同时固定 Compose 项目名。机器上并存多个 worktree 时，这三者可能不属于同一版本。启动或迁移可能作用于已有实例，旧分支随后也可能因 schema 版本不匹配而拒绝启动。见 [配置选择](../../dev.sh#L3)、[源码与项目选择](../../dev.sh#L18)。

建议把接管已有实例与创建独立实例分成明确操作。新实例要求指定环境文件和项目标识，接管时先核对源码根、配置来源、卷和数据库迁移计划，避免默默混用。

### E05 · 当前主远端的合并门禁尚未被仓库证明

当前 `origin` 是 Gitee。仓库跟踪的自动化入口在 `.github/workflows`，且推送触发主要覆盖主分支或发布分支。本地配置不能证明 Gitee 提交或合并会执行这些检查。若组织已配置外部流水线，需要在 Gitee 侧核对必需检查和实际运行记录。见 [核心门禁](../../.github/workflows/core.yml#L3)、[平台门禁](../../.github/workflows/core-platform.yml#L3)。

建议把依赖边界、静态检查、关键集成测试、构建和浏览器冒烟收敛成仓库可复用的校验入口，接到 Gitee 的合并阻断检查。以一个测试失败的改动无法合并作为验收结果。

## P2 · 按业务域收敛

### E06 · HTTP 路由仍穿过应用层，权限入口也有多套声明方式

部分助手接口直接调用 `container.assistant_conversations.store`，附件路由自己串联会话授权、模型能力和文件上传。后端架构检查能查私有模块导入，但只拦截 API 层对 `.store` 的少数方法名。Console 的权限又按模块名与函数名查表，已登记模块漏操作会拒绝，未登记模块先返回；部分模块按照规则交给领域授权。现有广场路由已登记，未发现通用越权，这里记录新增接口时的遗漏风险。见 [广场历史](../../backend/src/zhiheng/api/console/agents.py#L62)、[附件路由](../../backend/src/zhiheng/api/console/assistant_conversations.py#L65)、[后端门禁](../../tools/check_architecture.py#L199)、[权限分派](../../backend/src/zhiheng/api/common/platform_access.py#L307)。

建议先从广场历史与附件用例收回跨模块编排，明确每个用例的事务所有者。让新 Console 路由显式选择操作权限、领域内授权或公开入口，并用路由清单验证每个声明。保留已有导入检查。

### E07 · 持久执行类型与知识准备契约需要跨多处手工同步

Run 类型已有 `Literal` 约束，但准入、调度、执行复核和业务投影各维护自己的分派。增加受支持的类型时漏登记，部分授权与投影路径会直接返回。知识准备还通过可变回调表与通用字典跨异步边界传递请求，不同来源依赖的字段要在运行时重新解码。改动字段或新增来源可能在任务已经受理后才失败。见 [运行契约](../../backend/src/zhiheng/runtime/contracts.py#L44)、[执行复核](../../backend/src/zhiheng/application/execution/authorization.py#L96)、[知识准备状态](../../backend/src/zhiheng/modules/knowledge/retrieval.py#L76)、[回调装配](../../backend/src/zhiheng/bootstrap/container.py#L311)。

建议为运行类型校验授权、投递和终态策略是否完整，明确区分刻意无需处理与忘记登记。知识准备按现有来源定义带版本的持久契约，逐条迁移，不发明通用工作流框架。覆盖旧格式恢复和未知格式拒绝。

### E08 · 文件分页按行查询，复核后又改变游标语义

存储管理分页先计数和取行，再逐行调用 `FileService.info`，每行至少查一次引用数和一次授权；100 条基本页约 202 次 SQL，还未计入其他过滤与校验。资源 API 限量取候选后逐条复核，最后用复核完的长度判断下一页。候选在两次查询之间失去可见性时，本次页变短，仍有效的后续记录可能不可达。见 [管理分页](../../backend/src/zhiheng/modules/files/queries.py#L256)、[逐行投影](../../backend/src/zhiheng/modules/files/service.py#L282)、[候选复核](../../backend/src/zhiheng/application/files/queries.py#L44)、[游标判断](../../backend/src/zhiheng/api/resources/files.py#L121)。

建议先在同一查询或批量查询中完成受权范围与必要投影，再分页。若保留逐段复核，游标应反映已扫描的位置并保持有界扫描。用分页竞争条件与查询数断言验收，未来「我的文件」直接复用改好的查询，避免复制存储管理接口。

### E09 · 广场发布、运行和会话展示使用不同的版本判断

草稿与广场快照已分开，这是应保留的边界。目前广场只保存最新快照，历史会话展示优先读取当前上架版，下架后回退到会话创建时的配置。排队 Run 的执行守卫比较整个配置对象，只改名称或简介也会拒绝已受理的请求。运行审计虽保存模型实际配置，却未记录发布修订标识，定位同一助手哪次上架触发的差异较难。见 [发布写入](../../backend/src/zhiheng/modules/agents/service.py#L124)、[历史展示](../../backend/src/zhiheng/modules/agents/conversations.py#L314)、[执行守卫](../../backend/src/zhiheng/application/agents/execution.py#L256)、[运行审计事实](../../backend/src/zhiheng/modules/agents/orm.py#L30)。

建议明确展示字段、可执行配置和发布身份的关系，运行快照记录实际发布标识，明确更新或下架对排队、已开始和历史读取分别有什么影响。先补同一套规则和测试，等有业务回滚需求再增加历史发布管理功能。

### E10 · 下架助手仅从最近 12 条会话可找回

广场最近使用只按用户取 12 条，无分页。某助手下架且所有会话都移出这 12 条后，旧链接仍能读取，界面已经没有找到该助手旧会话的入口。见 [历史查询](../../backend/src/zhiheng/modules/agents/conversations.py#L152)、[广场入口](../../frontend/src/modules/agents/components/AssistantPlaza.vue#L144)。

建议保留轻量最近使用，并增加按用户授权、可分页的完整会话历史。用下架后超出最近 12 条的记录验证可达。

### E11 · 共享页面壳靠硬编码路由名，页签语义与实际面板分离

私人和广场聊天复用一个组件，应用壳却靠固定路由名数组决定会话布局和浮窗模式，新增广场路由未纳入。助手页签的 Ant Tabs 面板为空，实际内容是兄弟节点，辅助技术从页签找到的是空面板。见 [应用壳](../../frontend/src/app/App.vue#L90)、[浮窗](../../frontend/src/app/App.vue#L131)、[助手路由](../../frontend/src/modules/agents/routes.ts#L4)、[页签](../../frontend/src/modules/agents/views/AgentsView.vue#L20)。

建议由 RouteMeta 声明页面壳模式，两个真实面板归入对应页签插槽。继续保留页签各自的搜索、结果与滚动状态，验证移动端布局、键盘导航及 `aria-controls` 指向。

### E12 · 前端 HTTP 门禁与宿主隔离还未覆盖实际代码

前端依赖检查能阻止跨域导入私有文件，但直接 HTTP 调用规则只检查 `app` 层。知识库解析设置组件仍同时拼接协议、解码响应和维护表单。后台导入文件模块公开路由再调整地址，文件视图又注入后台缓存，文件模块的可复用性取决于后台宿主。见 [前端检查器](../../frontend/tools/moduleBoundaries.js#L87)、[解析设置](../../frontend/src/modules/knowledge/components/DocumentParsingSettings.vue#L76)、[后台路由](../../frontend/src/modules/admin/routes.ts#L16)、[文件页缓存](../../frontend/src/modules/files/views/FilesView.vue#L66)。

建议把协议归到所属模块的 API 文件，逐个迁出例外再扩大门禁。文件模块的路由与缓存由后台适配，或使用不依赖后台的通用接口。评审标准是依赖与责任归属，不是文件后缀是否统一。

### E13 · 大型控制器的拆分应以状态所有权为单位

知识库工作区控制器集中处理目录和路由、上传、查询、图谱、管理命令与后台观察，持有多个独立 `RequestScope`。在局部改动时，需要跨多个请求分支判断是否取消、刷新和清空。目录已有分离的上传、查询与图谱 composable，可继续沿现有模式收敛。见 [知识库工作区](../../frontend/src/modules/knowledge/composables/workspace.ts#L35)、[管理命令](../../frontend/src/modules/knowledge/composables/workspace.ts#L344)、[权限与后台观察](../../frontend/src/modules/knowledge/composables/workspace.ts#L655)。

建议一次只拆一类所有权，例如先提目录加载和文件夹导航，再移出独立观察。先固定取消、权限变化和晚响应行为的回归。助手编辑器与工作空间工具也有大文件，单看行数不足以作为立即拆分依据。

### E14 · 交付门禁覆盖了多数静态和集成检查，沙盒发布链仍有空档

核心平台流水线持有 PostgreSQL、Redis、向量与对象服务并跑真实构建和浏览器检查。它没有配置独立沙盒测试环境，工作空间的真实隔离及部分 Office 文件续写与发布用例会按夹具条件跳过。另有迁移头需要跨运行时常量、打包清单和测试夹具重复维护，容易出现源码迁移成功但应用拒绝启动。见 [平台服务配置](../../.github/workflows/core-platform.yml#L43)、[沙盒测试条件](../../backend/tests/core/integration/test_workspace_sandbox.py#L15)、[文档产物验收](../../backend/tests/core/integration/test_work_agent_execution.py#L279)、[启动版本](../../backend/src/zhiheng/infrastructure/database.py#L9)、[打包清单](../../tools/check_core_wheel.py#L300)。

建议单列有受控沙盒的发布门禁，区分跳过与通过。自动比对源代码 Alembic 单头、出包迁移和 API/Worker 预期版本，兼测空库和上一发布版升级。

## P3 · 文档同步

### E15 · 架构总览和工具链说明滞后于代码

总览仍写助手只维护最新配置和启用状态，广场已经增加独立发布快照。Python 版本也需要区分覆盖范围。包声明支持 3.10 起，核心流水线矩阵用 3.10 和 3.13 执行单元及打包检查，平台集成流水线使用 3.12。见 [架构总览](README.md#L68)、[包工具链](../../backend/pyproject.toml#L9)、[核心矩阵](../../.github/workflows/core.yml#L16)、[平台集成版本](../../.github/workflows/core-platform.yml#L49)。

建议注明各层支持及测试范围。若承诺用 3.10 完成独立部署，则用最低版本补关键集成冒烟。把广场的生命周期、授权和回退规则作为同一份架构说明持续维护。

## 值得保留的现有设计

- 后端把 HTTP 协议、业务编排、领域和运行时分开。供应商适配集中，已有 `public.py` 约束和静态规则作为基础。
- 多种模型入口共用 `RunAdmission`，Run、Outbox 和费用预占具备事务边界。调用者与付费身份显式存在，Worker 仍可在执行前复核授权。
- 前端按业务域隔离 API、页面与控制器，有共享的 `RequestScope`、SSE 解码和类型门禁。助手广场的专用公开 DTO 是合适的做法，应保留与完整配置的区分。
- 平台已有前后端边界单测、真实数据库与本地模型集成测试、浏览器夹具和显式迁移。优先让这些机制覆盖真实交付和新边界。

## 建议实施顺序

1. 在合入广场改动前，补降级保护、浏览器待确认数据清理，以及发布状态和既有历史的回归场景。
2. 把源代码工作副本与实例绑定、Gitee 门禁、Worker 维护隔离做成三项独立改动，分别验证。
3. 在开发「我的文件」前，收敛文件批量投影、授权和分页；在给广场助手开放知识库或技能前，收敛发布版本、执行策略与异步契约。
4. 后续改动按业务域收敛前端控制器和布局元数据，不安排全仓大重构。每次提交流程保留独立的行为回归与回退说明。

本轮通过后端 AST 架构检查、源码导出检查、部署脚本语法检查、133 项后端架构/打包/导出单测（含 47 项架构规则单测）、8 项前端边界规则单测，以及测试镜像内的源码模式启动检查。另执行了 `git diff --check`。问题依据静态代码和现有测试覆盖核对，未运行完整端到端套件、并发压测或真实模型调用，也未对运行数据库执行迁移或降级。
