# 平台功能与角色权限设计

状态：产品设计，尚未修改业务权限或用户授权。

## 当前源码情况

- backend/src/zhiheng/modules/identity/admin_permissions.py 的固定目录主要覆盖系统管理以及模型配置、模型测试、费率、积分和存储治理。
- frontend/src/modules/admin/views/RolesView.vue 从后端动态读取权限目录并分组展示；可以扩展现有角色系统。
- frontend/src/app/components/PlatformSidebar.vue 的前台导航目前固定展示。
- frontend/src/app/router.ts 的权限跳转主要面向管理后台，默认登录目的地和异常回退多处为 /chat。增加前台权限后需一起调整，避免跳入无权页面或循环跳转。
- 现有私人资源归属与知识库共享规则继续生效；功能权限不能扩大资源范围。

## 产品原则

每个模块都可以授权，但不是每个模块都有“管理”按钮权限。采用“访问、使用、维护”三个动作语义，按模块需要配置。

访问：浏览模块及本人有权查看的记录。使用：发起模型调用、检索或任务。维护：创建和编辑本人资源。工作台只有访问权限；私人会话重命名、删除归入访问后的记录自助管理，不单独拆权限。

菜单入口与后台管理分开：角色具有前台功能权限，不因此获得管理后台入口。模型管理、积分管理等沿用既有管理权限。

功能授权与资源授权同时满足才能使用资源。超级管理员可管理功能授权，但管理身份不自动获得别人的私人会话、助手和私有知识库正文。

## 角色编辑页

保留角色名称、状态、备注。在“功能权限”区域增加四个标签页，避免所有权限在同一长列表中混杂：

1. 平台应用：工作台、对话体验、智能助手、工作空间。
2. 资源能力：模型目录、知识库、技能。
3. 开发与用量：开发接入、用量与调用。
4. 平台管理：现有模型与凭据、模型测试、费率、积分、存储治理以及系统管理权限。

使用模块行加动作复选框的矩阵；不适用的动作显示横线。每行显示已选数量，并提供“选择本模块全部权限”。每个标签页显示已选总数，顶部显示角色合计。新建角色默认不勾选，提供“普通员工”“内容维护人员”等可编辑模板；模板只填充当前表单，不创建隐式权限继承。

权限描述使用业务语言，例如“创建和维护本人助手”，不写成“管理所有助手”。提交前摘要列明可进入模块及可以执行的主要动作。

## 推荐权限标识

以下是建议新增的代码，不代表现有代码已经支持。前台能力使用 platform 前缀，后台治理保留 ai 与 system 前缀。

| 模块 | 建议标识 |
| --- | --- |
| 工作台 | platform:overview:read |
| 对话体验 | platform:chat:read、platform:chat:use |
| 智能助手 | platform:agents:read、platform:agents:use、platform:agents:write |
| 模型目录 | platform:models:read、platform:models:use |
| 知识库 | platform:knowledge:read、platform:knowledge:use、platform:knowledge:write、platform:knowledge:share |
| 技能 | platform:skills:read、platform:skills:use、platform:skills:write |
| 开发接入 | platform:developer:read、platform:developer:write |
| 用量与调用 | platform:usage:read |
| 现有工作空间入口 | platform:work:read |

应用的使用权限要求同时有本应用访问权限；维护要求访问权限。编辑角色时勾选使用或维护会自动补选访问，取消访问时明确提示会同时取消依赖权限；后端也应验证依赖，不能只靠前端。

资源模块的访问与使用保持独立：知识库页面可以不开放，但获准资料仍可供助手检索；没有知识库使用权限则绑定资料的助手不能绕过限制。模型目录入口被关闭，不应直接导致普通聊天失效；模型使用权限与模型配置权限独立。

角色不设置“忽略资源权限”“查看全部私人内容”等开关。

## 默认角色与授权来源

- 普通员工：工作台、对话体验访问与使用、智能助手访问与使用、模型使用、知识库与技能使用、本人用量。是否开放模型目录、知识库和技能页面由企业选择。
- 内容维护人员：在普通员工基础上允许创建和维护本人助手、知识库和技能；共享知识库按企业政策单独勾选。
- 开发人员：在普通员工基础上允许进入开发接入、维护本人应用与 Key。
- 平台运营人员：按需授予模型配置、测试、费率、额度等既有治理权限，避免一律授予超级管理员。
- 超级管理员：管理功能授权；私人内容仍受归属和显式资源授权约束。

当前助手尚未共享，所以“使用助手”只允许使用本人拥有的已发布助手。不能将此权限解释为所有员工都能用所有助手；企业助手共享需另行实现。当前版本建议普通员工模板同时开放创建和维护本人助手，否则没有既有助手的用户仅获得“使用”权限也无助手可用；企业仍可按需撤回创建权限。

多个启用角色的授权取并集。第一期不引入角色级显式拒绝。用户详情建议显示“有效权限”和来源角色，解释取消某个角色后为何另一角色仍授予同一能力。

## 入口与撤权行为

- 菜单、工作台卡片、搜索结果、快捷入口按访问权限显示，不能从工作台间接暴露已关闭模块。
- 路由直接访问无权模块时展示无权限说明及可访问入口；登录后进入工作台或首个获准模块。没有任何功能时展示“暂未分配功能权限，请联系管理员”，保留个人资料和退出。
- 接口校验同一权限，隐藏菜单不能代替后端限制。复用的模型、知识库和技能选择接口按调用场景授权，避免有对话权限却因没有目录权限而加载失败。
- 仅撤回使用权限时，仍有访问权限的用户可以查看和管理本人历史，但不能继续产生调用；访问也撤回则入口与历史读取都关闭。
- 排队任务在真正执行前重新校验。已经开始的回复允许按原请求完成并结算；账号禁用等安全停用沿用更高优先级的会话失效策略。
- 网页开发接入权限与 API Key 调用授权分开处理。Key 继续满足已有应用、Scope 和资源授权，不能用网页入口隐藏代替外部 API 的授权策略。

## 迁移与落地顺序

1. 固化权限目录、动作依赖及默认角色模板。
2. 在现有角色编辑页增加分区与矩阵，先做可审阅页面。
3. 接通前台菜单、工作台入口、路由、登录与无权限回退。
4. 补齐接口、后台任务执行前的功能权限校验，保留现有所有权校验。
5. 迁移现有账号：将过去默认开放的能力显式写入可编辑的授权来源，例如为现有普通账号分配“基础使用者”角色。迁移记录原范围，避免升级后全部失去访问，也避免运行时隐藏放行。之后新账号通过创建用户时明确选择默认角色，不给所有账号强制叠加不可撤回权限。
6. 验证多角色并集、角色停用与撤权、管理员与私人数据边界、接口直调、模型选择、知识库检索以及历史只读行为。

本设计没有修改现有角色、菜单或接口行为。实施时需保证配置未完成之前不先启用阻断规则。
